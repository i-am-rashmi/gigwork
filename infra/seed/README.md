# Seed data

Reference data per city, generated by [`tools/locality-import`](../../tools/locality-import/README.md). Do not edit by hand; regenerate with the tool.

| File | Content |
|---|---|
| `<city>/zones.geojson` | Zone boundaries (simplified), property `name` only |
| `<city>/localities.csv` | `source_id,name,pin,lat,lng`: search shortcuts for "type your area or PIN" (`pin` may be empty) |

## How the seed reaches the database

The core's Maven build copies this folder into the jar (`seed/`), and Flyway applies it through **repeatable seed migrations** listed in `core/src/main/resources/db/seed-migrations.csv` (`description,kind,folder`; the description identifies the migration and must be unique). `cities.csv` columns: `slug,name,live,time_zone` (an IANA name such as `Asia/Kolkata`, validated when loaded; all-day busy blocks are read in it). A `reference` migration loads `categories.csv`, `specialisations.csv` and `languages.csv`; a `city` migration loads its row of `cities.csv` plus `<city>/zones.geojson` and `<city>/localities.csv`.

- **Editing a seed file is how reference data changes**, until Admin editing exists (Phase 3, FR-33/FR-34). After that the database becomes the source of truth and these files become the initial data only. A seed migration's checksum is a hash of the files it reads, so on the next start Flyway runs again exactly the migrations whose files changed (and none otherwise). Nothing fails on an existing database.
- **A reload makes the database match the files without deleting anything.** Every row in a file is upserted by its stable key (deterministic UUIDv5 IDs, so IDs never change) and is LIVE; a city's `live` flag comes from `cities.csv`. Rows of the same seed whose key is no longer in the files are set to **RETIRED**: for a city, its zones and localities; for the reference seed, categories, specialisations (also those of a retired category) and languages. A key that comes back is LIVE again. Retire by removing a line, never by editing the status in the database (a reload sets every row in the files to LIVE). A file with no rows is refused rather than retiring everything.
- Each locality's zone is computed by PostGIS on every load (the live zone covering the point, lowest id on a border, else the nearest), so changed boundaries move localities to the right zone.
- **Adding a city** needs no code: add its row to `cities.csv`, generate `infra/seed/<city>/` with the locality-import tool, and add a `city` line to `seed-migrations.csv`. A city migration hashes only its own row of `cities.csv`, so adding a row does not rerun the other cities.
- The loader fails the migration (and the start) if a file is missing, a row is malformed, or a specialisation names an unknown category.
- Repeatable migrations run after all versioned (SQL) migrations, ordered by description, so a seed migration never needs a version number and cannot collide with a SQL one.

## Notes for the loader

- **`source_id` is the stable key.** It is the smallest OSM element id among the places merged into the row, written as `type/id` (e.g. `node/3300149442`; smallest by numeric id, ties node, way, relation). It is unique in a file (the tool fails otherwise). Upsert localities by `(city, source_id)`; never by name or by row position. OSM ids are never reused. The key can change only if regeneration merges or splits places differently, so treat a source_id that disappears as a retired locality, not a deletion (nothing referenced is hard-deleted).
- **Names are not unique per city.** The same locality name can appear more than once (different places more than 1 km apart, sometimes with different PINs). Do not add a unique constraint on name and do not look localities up by name alone.
- `pin` may be empty.
