# Seed data

Reference data per city, generated by [`tools/locality-import`](../../tools/locality-import/README.md). Do not edit by hand; regenerate with the tool.

| File | Content |
|---|---|
| `<city>/zones.geojson` | Zone boundaries (simplified), property `name` only |
| `<city>/localities.csv` | `source_id,name,pin,lat,lng`: search shortcuts for "type your area or PIN" (`pin` may be empty) |

## How the seed reaches the database

The core's Maven build copies this folder into the jar (`seed/`), and Flyway applies it through **seed migrations** listed in `core/src/main/resources/db/seed-migrations.csv` (`version,description,kind,folder`). A `reference` migration loads `categories.csv`, `specialisations.csv` and `languages.csv`; a `city` migration loads its row of `cities.csv` plus `<city>/zones.geojson` and `<city>/localities.csv`. Every row is upserted by its stable key and gets a deterministic UUIDv5, so reloading changes nothing and every environment has the same IDs. Each locality's zone is computed by PostGIS (the zone covering the point, else the nearest).

- **A seed migration's checksum is a hash of the files it reads.** Editing one of those files after its migration ran fails Flyway validation, like editing an applied SQL migration. To change reference data after release, add a new seed migration that points at a new file, rather than editing the old one.
- **Adding a city** needs no code: add its row to `cities.csv`, generate `infra/seed/<city>/` with the locality-import tool, and add a `city` line to `seed-migrations.csv`. Use **the next free version number across SQL and seed migrations**; Flyway's duplicate-version check is the guard. Adding a city's row does not disturb earlier migrations, because a city migration hashes only its own row.
- The files are loaded as-is: the loader fails the migration if a file is missing, a row is malformed, or a specialisation names an unknown category.

## Notes for the loader

- **`source_id` is the stable key.** It is the smallest OSM element id among the places merged into the row, written as `type/id` (e.g. `node/3300149442`; smallest by numeric id, ties node, way, relation). It is unique in a file (the tool fails otherwise). Upsert localities by `(city, source_id)`; never by name or by row position. OSM ids are never reused. The key can change only if regeneration merges or splits places differently, so treat a source_id that disappears as a retired locality, not a deletion (nothing referenced is hard-deleted).
- **Names are not unique per city.** The same locality name can appear more than once (different places more than 1 km apart, sometimes with different PINs). Do not add a unique constraint on name and do not look localities up by name alone.
- `pin` may be empty.
